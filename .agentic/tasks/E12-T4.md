## Goal

Follow-up to PR #68, agreed by the product owner on 20 Nov 2026. Claude Code on Windows has a `PowerShell` tool, and its hooks docs use the matcher `Bash|PowerShell`. The factory's `.claude/settings.json` matcher and `CLAUDE_CODE_TOOLS` list only the spec's tools. So where the PowerShell tool is turned on, its calls skip the hook: a role can run any command, and locks don't apply. This slice maps `PowerShell` to the neutral `run` and adds it to the matcher.

## Acceptance criteria

- E12's tool table (spec) lists Claude Code's `PowerShell` tool under `run`. This is a spec change, for the product owner to approve.
- `CLAUDE_CODE_TOOLS` maps `PowerShell` to `run`, and the generated `PreToolUse` matcher includes it.
- A PowerShell call outside a role's `run` scope is denied, and an in-scope one is allowed. Its input is read from `tool_input.command`, as for Bash.
- The tests that pin the tool table and the Claude Code entry (E03 and E12-T2) are updated, through a relock the product owner approves.

## Notes

- Source: code.claude.com/docs/en/hooks.md, whose matcher example is `Bash|PowerShell`. The docs don't give the tool's input schema; the field `tool_input.command` comes from their PowerShell example. Check it against the docs before writing tests.
- No code for this in PR #68.
