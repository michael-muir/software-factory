# E12 · Tool adapters design note

Spec: [E12 spec](../specs/E12-tool-adapters.md) · Issue: [#12](https://github.com/michael-muir/software-factory/issues/12)
Status: **Accepted by the product owner, 19 Nov 2026** · ADRs: [0023](../adr/0023-adapters-write-committed-files-with-a-manifest-and-a-drift-check.md) · [0024](../adr/0024-one-hook-handler-recognises-each-tools-payload.md)

## Summary

There are two parts:
1. **A kit module, `.factory/adapters/build.py`,** standard library only (ADR 0023). It reads the roles and skills, using `agents.py`'s readers, and the repo's `[adapters] tools`. It builds every tool file in memory, then writes them, or with `--check` compares them with what's on disk. It also writes `.factory/adapters/generated.json`, a manifest of the paths it produced and their hashes, so it can remove files it no longer produces. The gate and `install.py` load it like `docs.py`.
2. **One hook handler in `agents.py`** (ADR 0024). `hook claude-code`, `hook copilot` and `hook cursor` share it. The handler recognises the payload by its shape, not by the name it was called with, because VS Code's Copilot and Cursor also read `.claude/settings.json`. It maps the tool name with that tool's table, resolves the role, calls E03's `allow`, and answers in that tool's protocol.

## Source layout

```text
kit/.factory/adapters/build.py         # compile, write, check, manifest; CLI: build.py [--check]
kit/.factory/agents/agents.py          # + Copilot and Cursor tool tables; payload recognition; hook copilot|cursor
kit/.factory/agents/copilot-hook       # sh launcher: Python 3.11+, then agents.py hook copilot
kit/.factory/agents/cursor-hook        # sh launcher: Python 3.11+, then agents.py hook cursor
kit/.factory/gates/gate.py             # + drift step, reported like docs (ADR 0020)
factory_installer/                     # install runs the build; check reports drift; config gains [adapters]
.claude/ .github/agents|skills|hooks/ .cursor/   # this repo's generated files (AC-12)
.factory/adapters/generated.json       # this repo's manifest of generated files
```

The kit's `.factory/adapters/.gitkeep` goes.

## Generated files

**Agents:** YAML front matter, written with JSON-style double-quoted strings (valid YAML, and readable by E10's subset reader), then this notice line, then the role card's body unchanged:

```text
<!-- Generated by .factory/adapters/build.py from <source>. Edit the source, then run build.py. -->
```

| Tool | Path | Front matter |
| --- | --- | --- |
| Claude Code | `.claude/agents/<name>.md` | `name`, `description`, `tools: "Read, Glob, Grep, Bash, PowerShell"` |
| Copilot | `.github/agents/<name>.agent.md` | `name`, `description`, `tools: ["read", "search", "execute"]` |
| Cursor | `.cursor/agents/<name>.md` | `name`, `description` |

The tool tables are the spec's, held as data in `agents.py` (`CLAUDE_CODE_TOOLS` already exists; `COPILOT_AGENT_TOOLS`, `COPILOT_HOOK_TOOLS` and `CURSOR_HOOK_TOOLS` are new). Copilot's `edit` covers both `edit` and `write`, so it's listed once.

**Skills:** every file in `.factory/skills/<name>/` is copied byte for byte to `<tool skills folder>/<name>/`. Skill files carry no notice, because their bytes must match the source.

**Hooks:**
- **`.claude/settings.json`:** the existing JSON is loaded. Any `PreToolUse` entry whose command names `.factory/agents/claude-hook` is replaced by the generated one. Every other key and entry is kept, in order.
- **`.github/hooks/factory.json`:**
  - `version` 1
  - one `preToolUse` command
  - `bash`: `sh .factory/agents/copilot-hook`
  - `powershell`: the shell-neutral command below, for `copilot-hook`
  - `timeoutSec` 10
- **`.cursor/hooks.json`:**
  - `version` 1
  - an existing file's other entries are kept, as for Claude Code
  - one `preToolUse` command: the shell-neutral command below, for `cursor-hook`
  - `timeout` 10
  - `failClosed: true`

**One command for every shell (amended 20 Nov 2026, before the live check).** A hook command can be run by more than one shell:

- Claude Code runs `.claude/settings.json` with `sh -c`, with Git Bash on Windows, or with PowerShell when Git Bash isn't installed.
- Copilot CLI also reads `.claude/settings.json`. It runs hook commands with PowerShell on Windows, and it doesn't set `$CLAUDE_PROJECT_DIR`.
- Cursor runs commands with PowerShell on Windows. It also imports `.claude/settings.json` by default.

So the first commands (`sh "$CLAUDE_PROJECT_DIR/..."`, `sh .factory/agents/cursor-hook`, and `python ...` for Copilot) blocked every call where sh wasn't on PATH or the variable wasn't set. `python` could also be the Windows Store stub or an old Python. Each of these hooks now runs:

```
git -c 'alias.factory-hook=!sh .factory/agents/<launcher>' factory-hook; exit $LASTEXITCODE
```

- **git runs a `!` alias with its own sh,** which Git for Windows brings, from the top of the repo it's started in, and passes stdin through. So no sh on PATH is needed, no variable, and no exec bit. A hook started in a subfolder still finds the launcher. The sh launcher then finds Python 3.11+, skipping the Store stub, as before.
- **The quoting works in every shell.** The single quotes are literal in sh, bash, PowerShell 5.1 and pwsh 7, and there's no double quote for PowerShell 5.1 to mangle on its way to git.
- **The exit code is kept.** `exit $LASTEXITCODE` keeps the exit code 2 that blocks a call, which `powershell -Command` would turn into 1. In sh it's a bare `exit`, which keeps git's code.
- **Copilot's `bash` command is unchanged,** because its cloud agent runs only `bash`, on Linux.
- **`agents.py hook` reads stdin as raw UTF-8 bytes and drops leading byte order marks,** which PowerShell adds when Cursor pipes the payload on Windows. Windows PowerShell 5.1 adds two, as CI showed.

`tests/test_adapters_shells.py` runs every registered command through sh, bash, `powershell` and `pwsh` wherever they're installed, on CI's three OSes. It also runs them through Cursor's PowerShell wrapper, with a PATH that has git but no sh, and with a byte order mark.

**Claude Code's PowerShell tool (amended 20 Nov 2026, after the live check failed on Windows).** On Windows, Claude Code has a `PowerShell` tool, which it treats as the primary shell once it's on. Its hooks docs use the matcher `Bash|PowerShell`, and give the tool Bash's input fields, with the command in `tool_input.command`. The factory's matcher listed only Bash, so a PowerShell call skipped the hook. In the product owner's live check, `ls` ran under the verifier role.

- `CLAUDE_CODE_TOOLS` maps `PowerShell` to `run`, and the generated matcher includes it. A subagent's `tools` is an allowlist, so a role with `run` lists both `Bash` and `PowerShell` in its agent file (product owner, 20 Nov 2026). Without `PowerShell` there, a role couldn't use Windows' primary shell; with it, the hook holds both to the same scope.
- The shell control check covers PowerShell syntax as well as sh's. PowerShell evaluates `(...)`, `$var`, `$x.Method()` and `@(...)` inside a native command's arguments, so `$`, `(`, `)` and `@` at the start of a word are control text. So is a line break of any kind. Copilot's `powershell` tool and Cursor's `Shell` on Windows go through the same check.
- A subagent's calls carry `agent_id` and `agent_type`, and the hook already reads `agent_type`. A call the main session makes has no `agent_type`, so only `FACTORY_ROLE` and locks apply to it.

`tests/test_adapters_powershell.py` covers these, with the docs' payload shape, and `tests/test_adapters_powershell_agents.py` covers the agent files.

**Writing:** JSON is written with `indent=2`, LF line endings and a final newline. Front matter keys are always in the same order. Files are written atomically (`state.write`).

## Build, check and manifest (ADR 0023)

- **The build** reads `.agentic/config.toml` `[adapters] tools`. The default is all three, and an unknown tool name is a config problem. It builds `{path: bytes}` for the chosen tools, writes what differs, and deletes the paths in the old manifest that aren't produced any more. Then it writes the new manifest: sorted paths with LF-normalised SHA-256s.
- **`--check`** builds in memory and reports `missing`, `stale` (bytes differ) and `extra` (in the manifest but no longer produced), one line each. It exits 1 if there are any.
- **The gate** runs the check on every run, after the docs step. Drift lines appear in the report (text `Adapters: N files, M stale`, and JSON `"adapters": {...}`). They fail the verdict, and the checks still run.
- **`install.py`** runs the build after it installs, and its `check` adds the drift lines to its problems.

## The hook handler (ADR 0024)

**Recognising the payload:**

| Shape | Tool | Name field | Arguments |
| --- | --- | --- | --- |
| `toolName` present | Copilot (CLI or cloud) | `toolName` | `toolArgs`, a JSON string or an object |
| `hook_event_name: "PreToolUse"` with `tool_name`, and a Copilot tool name | Copilot (VS Code form) | `tool_name` | `tool_input` |
| `workspace_roots` or `conversation_id` present | Cursor | `tool_name` | `tool_input` |
| otherwise `tool_name` | Claude Code | `tool_name` | `tool_input` |

**Paths:**
- **Claude Code:** `file_path`, or `notebook_path` for NotebookEdit.
- **Copilot:** `path`.
- **Cursor:** `file_path`, then `path`. If Cursor documents another key, the design adds it.

A write with no path is blocked.

**Mapping:**
- **Copilot:** `view` is read; `glob` and `grep` are search; `edit` is edit; `create` is write; `bash` and `powershell` are run; `web_fetch` is web.
- **Cursor:** `Read` is read and `Grep` is search. `Shell` is run. `Write` is allowed if the role lists `edit` or `write`, because Cursor doesn't tell them apart. `Delete` counts as write.
- **Unmapped names** (`task`, `ask_user`, MCP tools) are denied when a role is set, and allowed when none is (E03's AC-07).

**The role:**
- **Claude Code:** `agent_type`, then `FACTORY_ROLE`.
- **Copilot:** `agentType` or `agent_type`, then `FACTORY_ROLE`.
- **Cursor:** `FACTORY_ROLE` only.

**The answer:**

| Tool | Allow | Deny |
| --- | --- | --- |
| Claude Code | exit 0, no output | exit 2, reason on stderr (E03) |
| Copilot | exit 0, no output | `{"permissionDecision": "deny", "permissionDecisionReason": ...}` on stdout, exit 2 |
| Cursor | exit 0, no output | `{"permission": "deny", "user_message": ..., "agent_message": ...}` on stdout, exit 2 |

Exit 2 denies in all three tools, so a deny is honoured even if the JSON is misread. Every error goes through the deny path, as in E03.

## Test seams

- **Build:** `build.build(root) -> dict[str, bytes]` is pure. The tests:
  - parse each agent file's front matter with `agents.read_yaml_front`, and compare it with the tables
  - compare skills byte for byte
  - parse the hook JSON, and check that `.claude/settings.json` keeps the unrelated keys in a fixture
  - build twice, and expect equal bytes
  - drop `cursor` from the config, rebuild, and check that `.cursor/` files are gone and the manifest updated
- **Check:** in temp repos, each of missing, stale and extra is reported, the gate's report shows it, the verdict fails, and the checks still ran.
- **Hooks:** `agents.main(["hook", tool])` in-process, with payloads copied from each tool's documentation: Copilot's `toolArgs` as a string and as an object, its VS Code form, Cursor's `workspace_roots` form, and a Cursor payload sent to `hook claude-code`, which must be recognised as Cursor. Each test checks the exit code and the stdout or stderr protocol. The launchers are tested through `sh`, on POSIX only.
- **Done-when (AC-10):** one fixture role, built for all three tools. One out-of-list call in each tool's payload form gets a deny from all three, and one in-list call gets an allow.
- **Dogfooding:** this repo's `build.py --check` passes, and so does E03's locked settings test.

## Risks

- **Tool formats change.** All three tools changed theirs in 2026. Only the tables in `agents.py` and the writers in `build.py` touch them, and the tests pin the documented shapes. A tool change means changing a table and its test.
- **Cursor's `preToolUse` path field isn't documented,** and its agent name isn't sent. Cursor enforcement is weaker: roles need `FACTORY_ROLE`, and writes need a recognised path key or they're blocked. The live check (AC-11) shows how it behaves in practice.
- **Hooks can fire twice** when a tool reads both its own config and `.claude/settings.json`. That's harmless: both calls give the same decision, because the handler recognises the payload.
- **Timeouts fail open** in Copilot and Claude Code. The gate's lock check is the backstop.
- **Generated files are a lot to review:** about 100 files for 16 roles and 16 skills across three tools. The PR says they're generated, and CI's drift check proves they match their source.
